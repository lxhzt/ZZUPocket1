# 教务登录与资金权限：无账号条件下的核查

> 2026-10-28 后续发现：已找到学校正式开放平台及具体教务 scope、应用凭据和申请审核说明。[新核查结果](security-restricted-academic-auth-20261028.md)更新了下文“尚未找到明确教务 scope”的历史调查状态。当前还没有取得本应用的批准权限或验证数据主体限制。

日期：2026-10-27。依据：当前代码、七次受限公开页面 GET、学校公开通知及固定提交的社区源码。执行计划见 [工作计划](security-work-plan-20261027.md)。

## 结论

**发现了当前本科教务的独立网页会话候选方案。** 这比此前“尚未找到教务专用授权方式”的调查结果更进一步，但尚不能称为学校承诺的只读授权，也没有证明它不能访问或换取资金权限。

亲自访问当前教务网页登录入口，观察到：

```text
GET https://jwxt.zzu.edu.cn/student/sso/login
  302 → https://cas.s.zzu.edu.cn/cas/login?service=https%3A%2F%2Fjwxt.zzu.edu.cn%2Fstudent%2Fsso%2Flogin
GET 上述 CAS 地址
  302 → /cas/a/login?service=同一教务服务地址
GET 上述 CAS 登录页
  200 → 学校登录表单
```

三跳分别人工审阅后访问，不自动跟跳，不带 Cookie、令牌或账号，不提交表单。CAS 的 `service` 指定登录后要进入的服务，**不能据此把用户密码、CAS 全局会话或原生 JWT 的权限缩成该服务**。

## 哪些证据改变了判断

### 当前网页课表有 Cookie 数据通路

[拾光课程表适配配置](https://github.com/ShiGuangSchedule/shiguang_warehouse/blob/7c9e1907635cb1c2d481b316e6f52d69dc77edff/resources/ZZU/adapters.yaml#L8) 指定上述 CAS 登录页和教务回调为导入入口。[同提交适配脚本](https://github.com/ShiGuangSchedule/shiguang_warehouse/blob/7c9e1907635cb1c2d481b316e6f52d69dc77edff/resources/ZZU/zzu.js#L32) 对课表页、学期信息和课表 JSON 使用同源 `credentials: "include"`，这些查询中没有主动设置 `Authorization` 或 `X-Id-Token`。

这说明有近期社区实现依靠浏览器会话读取课表，可以研究“登录后只保留教务应用会话”的方案。它不证明浏览器登录期间没有 CAS 全局 Cookie，也不证明请求没有其他浏览器状态参与；未用真实账号复现。我们没有访问这些业务数据接口。

### 不能照搬通用令牌兑换会话的代码

[另一社区网页客户端](https://github.com/zzu-sensei/zzu_my/blob/59cbce00fbce56dcf0c196255ae94f963f2a11db/zzupy/web/eas.py#L33) 使用 CAS `/cas/t/login` 和同一个教务服务地址建立会话，但同时启用自动跳转，把通用令牌设置为两个请求头及 `.zzu.edu.cn` 域 Cookie。这种做法仍然接触广泛学校凭据，不能作为资金隔离的依据，当前安全分支未采用它。

### 旧系统不是可直接接入的替代品

`https://jw.v.zzu.edu.cn/eams/login.action` 当前仍返回旧登录表单，但同时明确显示“系统停用”并指向学校信息门户。因此不能因为存在用户名/密码输入框，就建议使用旧教务独立密码。

`https://jwxt.zzu.edu.cn/` 本次返回 301 到 `/eams`，后者返回 404。这只说明该入口在本次访问中的状态；不能据此认定整个教务系统停用，因为学生端 SSO 入口正常返回认证跳转。

### 官方资料支持统一登录，不提供资金权限隔离保证

[2026 年教务部通知](https://www5.zzu.edu.cn/jwc/info/1125/4859.htm) 指引学生通过信息门户进入本科教务学生端。[学校移动门户使用指南](https://www5.zzu.edu.cn/net/info/1023/2610.htm) 介绍同一官方 App 包含教务、一卡通和电费等服务。这些资料没有公开本次可依赖的教务只读 `scope`、JWT `audience` 或“不可兑换一卡通”的服务器契约。

[CAS 标准](https://apereo.github.io/cas/8.0.x/protocol/CAS-Protocol-V2-Specification.html) 要求 service ticket 绑定服务并限制验证次数；这是设计依据，不能替代学校实现验证。必须区分一次性服务票据、教务应用会话、CAS 全局会话和 App 的长期 JWT。

## 公开连接观察

- 七次直接访问全部采用系统默认 CA 与主机名校验，HTTPS/443；读取合计 267,282 字节，未执行下载脚本。逐请求状态、时间与哈希见 [证据](security-evidence/public-auth-20261027.json)。另通过网页检索工具读取两篇学校公开通知，其流量不计入该七次请求。
- 成功取得的 CAS 页面连接为 TLS 1.3，旧教务页面为 TLS 1.2；均通过正常证书校验。没有枚举其他 TLS 协议、密码套件或端口。部分跳转响应未提取到 TLS 元数据，不能据此推断其没有使用 TLS。
- 当前教务入口观察到 HSTS 和 `nosniff`；CAS 登录页观察到 `no-store`、`X-Frame-Options: DENY` 和 `nosniff`。这只是当前响应的属性，不是完整安全认证。
- 未登录响应中的部分 Cookie 没有显式 `Secure`，但带有 `HttpOnly`；不能把未登录的路由/预会话 Cookie 直接称为有效登录凭据。未尝试 HTTP 降级，也未验证可利用性。本应用原生请求强制 HTTPS，并把接收的研究生 Cookie 强制为 Secure。
- CAS HTML 引用了第三方统计脚本。未下载或执行该脚本；现有应用 WebView 的目标域限制会阻止该域。未观察到真实凭据泄露，不把静态引用认定为已经发生泄露。

## 实施选择与功能影响

| 方案 | 对资金凭据暴露的影响 | 功能/验证条件 | 当前决定 |
|---|---|---|---|
| 保留现有本科原生 JWT 查询 | 资金入口可由本应用阻断，但被盗 JWT 的学校权限没有改变 | 已有本地请求形态回归；无真实账号回归 | 保留，继续标明风险 |
| 在内嵌网页登录后仅保留教务 Cookie | 有望减少长期 JWT 与全局 SSO 的保存；登录过程仍位于本应用内 | 须核实实际 Cookie、服务器权限、课表和空教室功能覆盖 | 记录为候选，不把未验证实现直接替换现有登录 |
| 外部浏览器登录，导出课表后导入 | 应用可避免接触学校密码和通用会话 | 尚未找到学校现成的应用回调/可完整导入协议；空教室实时查询不自然具备 | 后续功能设计选项，不宣称已实现 |
| 使用已有离线/手工课表工具 | 不需要学校登录凭据 | 无法自动同步全部学校功能 | 保留现有本地功能，不用它冒充完整替代 |

若未来接入网页方案，应建立独立的教务客户端与会话存储，限定已核实读接口；只导入经过验证的应用会话 Cookie；不复制宽域 `userToken`、CAS `TGC`/`SESSION`；登录结束清理浏览器 SSO；请求过期时引导重新登录。**单纯修改客户端 Cookie 的 Domain/Path 不会缩小服务器授予该值的权限。**

## 本次可以与不可以确认的事

可以确认：当前学校提供教务服务的网页登录跳转；近期社区代码有 Cookie 课表导入；原生查询继续使用通用 CAS JWT；旧教务登录页面提示停用。

仍不能确认：登录后的教务 Cookie 是否严格限于教务、是否只读、能否兑换其他会话；学校是否向第三方正式开放受限授权；当前二维码/免密/支付验证和密码找回的后端规则；新的网页通路能否完整替代空教室等功能。没有把这些未知事项通过支付或越权请求进行试验。

因此，更准确的结果是：**已找到可以进一步实现权限分离的具体候选路线，但“正常使用全部在线功能且保证应用被攻破也不危及资金”的目标仍未获得证明。** 本轮的局部整改和本地对抗验证见后续执行报告，不等同真实设备测试或学校后端渗透测试。
