# 官方受限教务授权的核查结果

日期：2026-10-28。范围：官方公开申请流程、开发者指南与 OpenAPI 规范；不使用账号、不调用认证或业务数据接口。

## 核心结论

**已找到官方的应用级 OAuth2 / scope 授权机制，以及具体的本科、研究生课表和教室相关 scope。** 这更新了此前“尚未找到明确教务 scope”的调查状态。应优先研究通过学校正式审批取得独立应用权限，而不是继续把通用 CAS userToken 或网页登录 Cookie 当作权限隔离方案。

**已证实的是文档中的授权设计和接口划分，还没有取得已批准的应用凭据或验证后台实际执行。** 特别是，应用级数据权限不等于“当前学生只能读取自己的课表”；不能把这些权限及 ClientSecret 放进 Android 客户端，也不能据此立即宣布资金与隐私风险已经消除。

## 官方依据

1. 学校信息化办公室、网络管理中心在 [2026-09-20 的开放平台申请流程](https://www5.zzu.edu.cn/net/info/1096/2774.htm)中公布开发者注册、材料审批及获批接口的路径，入口为 [学校开放平台](https://open.s.zzu.edu.cn/)。本轮已用程序读取实际页面，不只依赖搜索摘要。
2. [技术指南](https://open.s.zzu.edu.cn/docs/index.html#/newguide/3.technology)明确把 scope 作为应用 API 权限单元；一个 scope 至少含一个接口，不能只申请组内某个接口。因此，必须核对获批 scope 的全部接口，不能只看名称。
3. [OpenAPI 对接说明](https://open.s.zzu.edu.cn/docs/index.html#/newguide/6.openAPI)描述应用 ClientID / ClientSecret、scope 申请审核、API 详情和返回字段申请。不是替换 App 中的一个令牌字符串就完成接入。
4. 由公开首页引用的配置和文档索引，追踪到[数据集市规范](https://poa.s.zzu.edu.cn/_docs/dataMarket/v1/latest/)。其 OAuth2 定义采用 `clientCredentials`，每个所选教务操作明确声明对应 scope。

这里的 OAuth2 是应用级凭据方案；没有发现并核实适合任意手机应用直接采用的用户委托 PKCE / 教务只读授权流程，不能把一般 OAuth 介绍当作学校已支持该流程的证明。

## 找到的具体教务 scope

以下名称直接取自学校公开的数据集市规范，不是根据接口路径猜测或自行发明的。规范文件版本标识为 `dataMarket-v1-2025_02_13_14_13_52.yaml`，在本轮访问时仍由 `latest` 页面引用。

| 官方描述 | scope | 作用与待核实事项 |
|---|---|---|
| 本专科生课表信息 | `dataMarket:v1:view_lima` | 可作为本科课表首选候选；描述含学号、课程名称、学期、周次、星期、授课时间、教学地点 |
| 本专科生教室使用信息 | `dataMarket:v1:tgxjxbzksjssyxx` | 可作为空教室占用数据候选；仍须核实刷新时效、时间解释与覆盖范围 |
| 本专科生教室基本信息 | `dataMarket:v1:tgxjxbzksjsjbxx` | 教室基础信息候选；只申请查询所需字段 |
| 本专科生排课信息 | `dataMarket:v1:tgxjxbzkspkxx_alpha` | 仅在前三项不足以提供必要功能时申请，避免重复扩大数据范围 |
| 本专科生课程信息 | `dataMarket:v1:view_papa` | 仅在课表缺少必要关联信息时申请，不默认申请全部课程数据 |
| 研究生课表信息 | `dataMarket:v1:view_echo_papa` | 研究生课表首选候选；描述中含学号、周次、星期、教学地点等字段 |
| 研究生排课信息 | `dataMarket:v1:view_delta_yankee` | 研究生课表必要补充候选，具体关联关系仍需校方说明 |
| 研究生教室基本信息 | `dataMarket:v1:view_delta_whisky` | 研究生教室基础信息候选，不等于已有实时空教室服务 |

对本次获取的数据集市规范的 320 个路径做本地分析后，这八个 scope 在该规范内各绑定一个所列教务操作，没有在同一规范中被列为资金或 IdToken 签发操作的授权条件。这支持“可单独申请教务权限”的方向；不能扩大为其他网关、未公开操作和实际服务器已经拒绝跨权限调用的证明。

这些操作在规范中使用 POST 查询，不应仅按 HTTP 方法把它们判断为业务写入。我们没有发送任何 POST，也没有执行这些查询。

## 必须保留的隐私边界

所选操作使用应用级 `clientCredentials`，路由为数据视图的 `/full` 操作，响应包含分页结果及数据行。公开描述没有列出请求参数或 requestBody，也没有说明会自动绑定当前学生身份。课表数据行则明确含 `XH`（学号），本科还含姓名等字段。

因此：

- “仅能访问教务接口”与“只能访问本人的教务数据”是两项独立要求。前者有文档候选，后者还缺服务端执行契约。
- 不能在手机上保存 ClientSecret，不能下载整批学生课表到手机后再做本地筛选。
- 优先要求校方提供当前学生范围的查询或受限视图；若只能提供经审批的数据集，需在校方批准的后端环境处理，后端依据可信登录身份绑定学号，并逐项校验访问权限，只向 App 返回本人必要数据。
- 后端托管本身不会自动消除批量数据凭据的风险。仍须限定授予的数据范围、字段、调用者、期限、审计和撤销措施，并审计后端；不能把它当作只靠客户端即可完成的整改。
- 文档字段足以说明这些 scope 与课表、教室功能有关，但格式、数据时效、完整覆盖和可用性没有通过真实账号验证。不改成一个未经验证的新登录方式来冒充“功能完整保留”。

## 明确排除的权限

- [IdToken 服务规范](https://poa.s.zzu.edu.cn/_docs/idToken/v1/latest/)定义 `idToken:v1:createIdToken`，可按账号取得 IdToken。这是高影响身份签发能力，不应申请给课表应用，更不能把它当作“无需学生密码”的安全捷径。没有调用该接口，也没有尝试取得任何 IdToken。
- [授权服务规范](https://poa.s.zzu.edu.cn/_docs/authz/v1/latest/)中的 `authz:v1:readRole` 面向应用角色、账号及组查询，不是教务只读 scope 的替代品。
- 公开目录中的数据中心当前优先主版本 v3 描述财务缴费明细，声明 `date:v3:TCJF`；本目标不需要，排除。我们先读取过仍在目录中的旧 v1 页面，随后纠正到 v3 并只分析 v3 规范，没有用 v1 推断当前范围。
- 不申请一卡通、支付、充值、退款、余额、全局身份签发、用户安全管理或无必要的批量人员数据权限；不使用通配 scope。每次权限组或接口定义变化，都需要重新核查。

## 推荐接入路线与准入条件

优先路线是“学校审核的独立应用 + 必要教务 scope + 校方批准的后端 + App 自有受限会话”。学校应用密钥只留在后端，App 不持有统一密码、通用 CAS JWT、CAS 全局 SSO Cookie 或平台 ClientSecret。

用户身份确认和教务数据授权必须分别解决。可以向学校提出身份属性/一次性回调方案，但尚未核实学校为这个应用支持哪一种具体协议，不能伪造 callback、clientId 或直接实现。若登录方案仍让 App 或其后端长期持有可跨服务取得资金权限的用户凭据，就不能登记为已经实现资金隔离。

公开审批表要求申请单位、单位审批意见、校内数据中心 IP 与学校二级域名等信息。已提取文字并渲染检查其一页内容；这是正式准入条件的线索，不是个人开发者已经获准使用、也不是校方必然会批准本应用的保证。申请对象、部署条件及能否为本项目提供受限视图仍需校方确认。

已准备[最小权限接入需求](security-academic-openapi-request-20261028.md)，可用于后续技术审核。未代注册开发者账号、提交材料、联系人员或建立后端服务。

## 本轮访问与证据

程序共读取 **23 个经逐项审阅的公开资源，响应体合计 1,777,809 字节**，包括指南、空白审批表、公开页面/配置与静态接口规范。逐次请求、哈希、候选 scope 与字段证据见[机器证据](security-evidence/restricted-academic-auth-20261028.json)。网页检索及索引页面读取另行记录，不混入该程序计数。

没有登录、Cookie 回传、脚本执行、令牌请求、接口注册、验证码识别、端口或目录扫描、学生数据读取、资金操作或压力测试。系统集成 DOCX 附件返回验证码页面后停止该路线；没有绕过。文档目录曾返回 HTTP 跳转，未跟随；人工审阅后仅通过 HTTPS 读取规范斜杠地址。

原始规范、配置、附件和网页保留在忽略目录中，不复制整份业务规范或配置到仓库。公开配置中的 `JWT_SECRET` 实际为空，其他若干设置是未替换占位符，没有把这些字段名称直接当作秘密泄露，也未使用任何配置值尝试认证。

结论的层级是：**已经找到正式、具体、可走审批流程的教务权限候选；尚未取得本应用的授权，也尚未验证数据主体限制与跨服务拒绝。** 下一步的实质工作是校方确认最小权限和接入条件，取得受限授权后再进行获准的非资金验证，而不是继续用未登录请求猜测权限。
