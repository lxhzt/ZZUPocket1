# 学校公开前端资金权限分析

> 后续的教务独立会话线索及正常公开访问证据见 [2026-10-27 认证核查](security-auth-scope-investigation.md)。本页保留资金前端静态分析及其结论边界。

核查日期：2026-10-26。对象：`ecard.v.zzu.edu.cn` 公开 H5 静态资源，以及 ZZUPocket 原始实现。

## 结论

公开前端可以进一步解释资金操作的客户端流程，但不能证明服务端权限控制有效，也不能证明存在可利用漏洞。

**不能将“令牌之外一定需要独立支付密码”作为资金隔离依据。** 电费页面是否要求支付密码受运行时配置 `needPwd` 控制；付款码组件可见调用没有统一的密码输入步骤。学校当前实际配置、二维码用途、服务端设备约束与交易限额均未验证。

上一轮从社区代码观察到的“电费充值传入支付密码”只描述该社区实现采用的方式；本次学校前端代码证明它不是所有客户端分支的必然条件。

## 访问范围与证据可信度

- 本轮串行读取 12 份公开资源：1 份 HTML、1 份主脚本、10 份该主脚本明确引用的页面或公共组件脚本。
- 全部是普通 HTTPS GET；总响应体 1,455,779 字节，全部返回 200；每个请求有大小与超时限制，不跟随重定向，未执行下载的 JavaScript。
- 没有登录，没有提供账号、密码、Cookie 或令牌，没有调用业务 API，没有发送短信、生成付款码、校验身份、提交支付、退款或转账。
- 没有端口扫描、接口枚举、参数猜测、验证码尝试、漏洞利用或压力测试。
- 主脚本 `index.c1a092dd.js` 的 SHA-256 为 `60c120194bc3481f9a2aa2e37961a4b7530d847daea9684388176bd2217dd1a1`。
- 请求清单、资源哈希和摘录位置见 [结构化证据](security-evidence/public-frontend-analysis.json)。原始静态副本保存在本地忽略目录 `.security-tools/public-frontend-20261026/`，未发布到仓库。
- 这些是客户端源码证据。通用前端可能包含学校未启用的功能；代码存在不代表功能已开放。未获得服务端源码、正式权限说明或运行时配置。

## 原作者从哪里分析

原项目 `docs/interfaces/接口现状核查.md` 记录了三种来源：公开 H5 的主脚本及懒加载页面、社区 ZZU.Py 实现，以及作者连接手机后对官方 App WebView 的本地调试。文档的 `127.0.0.1:9333` 是电脑转发到手机 WebView 的本地端口，不是学校服务器端口。文档另有历史 80/443 连通性记录，本轮没有重复连通性探测。

## 逐条发现

### 1. 登录令牌、交易标识和请求加密是不同层次

主脚本请求包装器通常从全局状态或本地存储读取一卡通 `accessToken`，设置 `Authorization`。对一组敏感操作，包装器先取得 `transactionId`，再随请求发送。部分操作还有 SM2/SM4 请求或响应封装。

这些流程说明存在额外交易处理，但**不能证明交易标识绑定了用户确认、支付密码、设备或单笔金额**；加密封装也不等于授权校验。没有对交易标识获取接口发请求，不能断言“只有令牌即可付款”，也不能把该标识认作独立二次认证。

### 2. 电费支付：密码由配置控制

电费页面将配置响应的 `resultData.needPwd` 赋给 `needPsd`。校园卡支付分支在 `needPsd` 为真时显示密码组件；否则构造金额等参数直接进入支付方法。密码组件在需要时把用户输入作为 `password` 交回页面。

这证明前端支持需要密码和不输入密码的两种流程。未读取配置接口，不知道学校、用户、支付方式或房间对应的实际 `needPwd` 值；也未验证服务端是否另有认证或强制检查。

### 3. 卡间转账：可见页面会提交支付密码

转账页面确认金额后显示 PIN 输入组件，将输入加入交易参数的 `password` 字段，再调用转账方法。主脚本包装器同时附带一卡通令牌及交易标识。

这是转账客户端具有密码步骤的明确证据，尚不足以证明后端会拒绝所有缺少该步骤的请求。未尝试绕过，也没有验证功能是否对当前学校和个人身份启用。

### 4. 全额退款：先验密码，再提交退款

读取到的全额退款页面会先调用密码校验方法，再调用退款方法；最终退款参数中未见再次携带该密码。服务端可能通过会话状态等方式关联先前校验，客户端源码无法确认关联是否存在、如何绑定、持续多久。

因此这是需要学校说明的授权边界，**不能据此认定可以跳过密码退款**。该页面也存在零余额分支，不能将其与有资金的退款条件混同。

### 5. 密码重置：必须关注身份信息与资金权限之间的间接关系

重置入口读取运行时配置，根据类型选择证件信息核验或短信核验。身份核验成功后，页面进入新密码输入与提交步骤。页面还包含不同身份、未绑定手机及其他授权入口的分支。

未读取配置或触发核验，不能确认学校是否允许证件方式重置，也不能确认是否存在更强的后端校验。**如果某部署允许凭已泄露的身份资料完成重置，支付密码就不能独立阻断该类风险。** 这是条件性风险，不是本次已证实的漏洞。

### 6. 付款码与扫码：不能假设每次都要求支付密码

二维码公共组件先读取虚拟卡配置，再获取在线码；可见在线码调用参数中只有码类型，没有支付密码。该组件还包含离线码、设备标识和支付结果处理。实际能否取得可支付的码，受服务端、设备、身份、配置及码用途等条件影响，未验证。

扫码页面的可见逻辑先携带二维码与交易标识提交处理，遇到特定服务端返回状态时再弹出 PIN 输入。由此只能确认密码要求可能由服务端条件决定，不能确认所有扫码都需要密码或都可免密。

本轮没有生成任何码，也没有扫描任何码。二维码失效时间、单次使用、交易限额、设备绑定和资金实际可用性均未知。

### 7. 敏感日志：静态代码存在明确的输出语句

全额退款脚本包含将 PIN 输入传给日志方法的语句；电费页面也会将支付参数传入日志方法。二维码公共组件含离线密钥相关数据传入日志方法的代码。

这些是需要审查的敏感输出点。未登录、未执行脚本，未观察到真实密码或密钥，也没有证据证明数据被上传给第三方；日志包装器在具体运行环境中的行为及实际可见性尚未验证。不能把静态输出语句直接表述为“已发生泄露”。

## 对 ZZUPocket 的影响

- 客户端删除校园卡、电费等代码，只能减少该客户端的功能和攻击面，不能缩小学校服务端授予通用 CAS 令牌的权限。
- 原始项目存在 CAS 令牌换取一卡通二级令牌的实现。与此次前端发现结合，资金风险评估需要同时覆盖令牌、密码重置、二维码及免密配置，不能只看是否保存支付密码。
- 当前安全分支仍阻断资金请求，且没有开放一卡通 H5。学校前端中的敏感日志语句不等于当前原生 App 已执行这些语句。
- 要取得更强的资金隔离，应优先使用学校服务端提供的教务专用只读授权。若无此能力，完全不让 App 接触通用学校凭据、改用离线导入，能更直接减少该 App 引入的凭据风险。

## 本轮不能回答的问题

学校当前是否开启免密；每种二维码是否可扣款；令牌是否绑定设备；支付密码能否仅凭身份信息重置；退款是否强制绑定先前密码校验；交易标识是否防重放；错误次数限制、限额、风控和支付密码与登录密码是否独立。

这些问题需要学校提供正式说明、服务端配置或授权测试环境，不能通过本轮静态分析作安全保证。本轮不继续向业务接口求证。
